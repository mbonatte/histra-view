### Non-negotiable preprocessing rule

When Python solves or performs a parity/strategy benchmark from an HRX, it
must generate its own Quad, interface, afference and spring objects.  Saved
HRX interfaces and spring definitions are **not** Python solver input.  They
may be parsed only as a C# reference during a comparison.

This invalidates the latest base-spring/P-Delta diagnostic.  It accidentally
used:

```python
model = load_model(hrx_path)
ModelManager.prepare_model(model)       # `force=False`: returns early if ready
```

`histra.preprocessing.prepare_model.prepare_model` deliberately returns
without rebuilding if `inspect_solver_readiness(model).is_ready` and `force`
is false (lines 175--202).  Consequently, a loaded locked HRX retained its
serialized interfaces/springs.  The required clean path is currently:

```python
model = load_model(hrx_path)
report = ModelManager.prepare_model(model, force=True)
assert report.prepared
session = AnalysisSession(model, strategy_policy="warn")
```

`force=True` rebuilds Quad springs, regenerates interfaces via
`_generate_interfaces`, reassigns afference, and creates interface springs
from Python material/geometry code (lines 224--245).  Before continuing any
benchmark, prove that this path is used and add a regression test which
corrupts/changes serialized springs but demonstrates identical freshly
prepared Python spring definitions.

The previous conclusion that only base interface 682 / Transversal1 spring 8
had a 100,000x tangent discrepancy is therefore **withdrawn**.  It is not
evidence of a C# `.Results`/HRX inconsistency, P-Delta defect, or model-point
projection defect.  Do not cite or act on it until all four matched benchmark
pairs have been rerun with fresh preprocessing.

The invalidated document is retained only as an audit trail at
`docs/investigations/benchmark-3-base-spring-reference-consistency.md`; its
content must not be used as evidence.  The earlier P-Delta comparison HTML in
the Codex visualizations directory is likewise non-evidence.

## What has been implemented in this worktree

These changes exist, but they are mostly uncommitted.  Review, test, and
commit them in focused groups; do not assume every item is release-qualified.

### Solver correctness and capability boundaries

- Static Quad/Interface V1 capability gates were strengthened.  Unsupported
  C# domains/enums fail at preflight rather than silently choosing a different
  physical law or solver.
- HRX loading preserves load metadata (including `TypeLoadDistribution`,
  `ForceImposed`, and `ForceControl`) and rejects unsupported static
  distributions rather than treating them as ordinary force loads.
- ArcLength work includes C# `ArcLength1` corrector/line-search sequencing,
  segment-tangent parity, and safeguards against opt-in cutbacks silently
  changing Standard to Modified tangent behavior.
- Force-equilibrium auditing and production-safe endpoint policy were added
  while retaining an explicit C#-compatibility behavior.
- Restart/state transfer and interface material-change paths were extended;
  `histra/tools/interface_chain_benchmark.py` and related tests/evidence
  exercise the five-stage interface chain.
- P-Delta `EachStep` / `EachIteration` paths exist and are tested, but their
  release strategy qualification is not complete.
- Modal paths, mass/eigen checks, and supported scope are documented; dynamic
  nonlinear, response-spectrum, Frame/Slab/Link/Joint, and concrete/steel/
  fiber systems remain explicitly out of V1.

### Compiled hot-path enforcement and performance work

- The backend coverage/lifecycle implementation is in
  `histra/solver/backend_coverage.py` and related runtime/topology modules.
  The intended rule is fail-closed: public production numerical steps must
  use compiled NumPy/Numba coverage and must not fall back to raw scalar
  Python after initialization, restart, or interface rebuild.
- Hysteretic runtime/batch scatter/transverse code was refactored for compiled
  operation.  This needs a final audit using fresh models and targeted tests
  of every lifecycle transition.
- `histra/tools/strategy_benchmark.py` produces candidate matrices, captures
  runtimes/iterations/factorizations and selects recommendations only among
  safe, response-preserving candidates.  Public advisor/warning API exists
  (`SolverStrategyAdvisory`, `SolverStrategyReport`,
  `SuboptimalSolverStrategyWarning`, `inspect_solver_strategy`, and
  `strategy_policy="warn"|"off"`).  It must not make a recommendation from
  any invalid/stale matrix.
