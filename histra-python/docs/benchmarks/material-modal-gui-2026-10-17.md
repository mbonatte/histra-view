## Why the elastic reference loses its foundation reaction

The original `DBModelManager/dbOutputManager.cs`,
`UpdateSpringStates(IEnumerable<SpringStateDBclass>, bool)`, compares the new
spring type with the saved row's type. If they differ, it logs a critical error
and continues without restoring that spring. Newly constructed springs retain
their virgin state. This differs from calling the lower-level
`SpringStateDBclass.SetSpring(false)` directly, which dispatches on the target
type and can restore the common fields across these types.

`Invoke-InterfaceRestartTypeGuardOracle.ps1` calls the actual guarded routine:
both Hysteretic-to-Elastic and Elastic-to-Hysteretic leave the new target at
zero force/displacement. A same-type control restores the nonzero source.
The [native receipt](../../release-evidence/material-modal/2026-10-17-native-db-type-guard.json)
records the observations and original assembly hash.

The GUI Results agree with that observation. In the elastic case, signed
vertical reaction R3 changes from -68.9599609375 kN at the end of Vert to
7.4505805969e-8 kN at the first Cycle_B commit and approximately zero at its end.
The stiffness case retains approximately -68.96 kN. This is a restart history
loss associated with the type guard, not an alternative diagonal-spring formula.
No C# runtime patch was made to obtain these observations.

Python's existing rejection of this transverse cross-law mutation remains
atomic: the old model/history are restored and the session remains usable.
Silently enabling the low-level cross-law transfer would preserve history
but would not reproduce the original GUI restart. Silently skipping history
would also contradict the API's requested state preservation. The selected
policy therefore keeps rejection by default and requires an explicit
`spring_type_change="csharp_reset"` at the mutation to reproduce the native
skip. It emits `SpringHistoryResetWarning` and reports each discarded spring
history, while retaining matching spring histories. The same type guard applies
to Elastic/Coulomb changes; their low-level history transfer must not be mistaken
for the guarded DB restart. See the [API guide](../guides/analysis-chains.md).

## Python correction and tests

The native spring experiments exposed an elastic compatibility-field defect.
`SpringLinearElastic.setTrialStrain` updates the dedicated trial fields, while
base F/U are copied at Commit. Structural callers separately set the base U
target before evaluating a spring. Python now preserves this distinction in
the scalar spring and compiled runtime object projections. Elastic Quad
import also retains the actual trial/committed fields and restored tangent,
instead of reconstructing force as K times U.

Six original-assembly histories distinguish direct spring calls from the
structural caller's displacement-target assignment. Tests check both modes,
then verify runtime import/projection for transverse, sliding and Quad slots.
The tests qualify these fields and histories, not general elastic-Quad analysis
or loaded cross-law support. Older elastic tests were corrected to check trial
response through the getters and committed response through F/U.

Windows Python 3.12 after the policy addition: 929 passed, 14 skipped and 1,665
subtests passed; the two existing P-Delta independent-equilibrium warnings remain
visible. Focused Ubuntu checks passed 20 tests, with 10 skipped (nine original
Windows UMFPACK cases and one optional benchmark). Backend job propagation,
reset reports, all three spring groups, warning-as-error rollback and failed
backend-validation rollback are covered. Broader
interpreter/package checks and the large Dhir/Article regressions were not rerun.
