# HiStrA-Python v1.6.0 Critical Code & Performance Assessment

**Date**: 2026-10-15  
**Scope**: Codebase changes from v1.4.0 (`c04ea6c`) to v1.6.0 (`b276c9b`)  
**Audience**: Maintainers and implementing agents

---

## 1. Performance Benchmark Results

Empirical side-by-side benchmark conducted on the same Linux host (`Python 3.12`, `SuperLU`, native compilation enabled):

| Benchmark / Operation | v1.4.0 (Before) | v1.6.0 (Current) | Difference | Finding |
|---|---:|---:|:---:|---|
| **Model Preprocessing** (`model-live`, 5 runs) | 14.42 s | **1.37 s** | **10.5x Faster** 🟢 | Greatly reduced initialization overhead. |
| **Model Preprocessing** (`Bridge_1`, 1 run) | **6.14 s** | 6.93 s | ~12% Slower 🔴 | Added native geometry checks add slight overhead on larger meshes. |
| **Solve: Vert** (`model-live`, 5 steps) | 28.20 s | **1.45 s** | **19.4x Faster** 🟢 | v1.4.0 suffered from first-step JIT lag; v1.6.0 executes compiled kernels immediately. |
| **Solve: Live Load** (`model-live`, 25 steps) | **0.422 s** | 0.466 s | ~10% Slower 🔴 | Small-step iteration loops have slight Python overhead from extra checks. |
| **Snapshot: Small Model** (`model-live`, 200x) | **0.0040 s** (fresh) | 0.0138 s (reuse) | **3.45x Slower** 🔴 | **Severe regression on small arrays.** Buffer validation overhead dominates. |
| **Snapshot: Large Model** (`Dhir`, 30x, 17 MB) | 0.2335 s (fresh) | **0.1411 s** (reuse) | **1.66x Faster** 🟢 | Avoiding OS page re-allocation on large buffers yields ~8.5% Newton step speedup. |

### Performance Takeaway
- **Large Models**: Net positive. Memory allocation relief on massive spring state buffers (~17 MB on Dhir) speeds up Newton iterations.
- **Small Models**: Buffer reuse in `HystereticBatchRuntime.snapshot(reuse=...)` is **3.5x slower** than plain `.copy()` because of quadratic validation loops (`np.shares_memory()` and shape/dtype checks).
- **Suggestion**: Guard buffer validation so it only runs on the first capture, or set a minimum buffer size (e.g., skip reuse if total buffer size < 1 MB).

## 2. Critical Architectural & Numerical Findings

### Finding A: Re-introducing Known C# Bugs in Domain Logic
- **File**: `histra/types/convergence_test.py` (lines 130–147)
- **Problem**: In v1.4.0, `ConvergenceTest.get_copy()` intentionally fixed a C# bug where copying an unbalance force test returned a displacement test. In v1.6.0, this was reverted:
  ```python
  force = self.criterion == "ForceMoment"
  return ConvergenceTest(
      max_u=float(self.norm_type) if force else self.max_u,
      criterion="DispRotation" if force else self.criterion,
      ...
  )
  ```
- **Risk**: A caller requesting `test.get_copy(iterations)` on a force convergence test **silently gets a displacement test** with its norm type hijacked as `max_u`.
- **Suggestion**: Do not corrupt domain model methods to mimic solver bugs. If required for legacy regression, gate this behind an explicit argument (e.g. `csharp_quirks=True`) or localize it to the C# test runner.

---

### Finding B: Dangerous Exact Zero Equality in Arc-Length
- **File**: `histra/solver/arc_length.py` (lines 570–614)
- **Problem**: Default constraint mode (`"csharp"`) replaces numerical tolerances with exact zero equality:
  ```python
  def is_zero(value: float) -> bool:
      return value == 0.0 if self.constraint_mode == "csharp" else abs(value) < 1e-30
  ```
- **Risk**: In floating-point arithmetic, comparing `value == 0.0` on a quadratic coefficient $a$ means $a = 10^{-20}$ evaluates to `False`. The code then computes:
  $$\Delta \lambda = \frac{-b \pm \sqrt{b^2 - 4ac}}{2a}$$
  Dividing by $2a \approx 2 \times 10^{-20}$ causes catastrophic numerical magnification, ill-conditioning, or overflow.
- **Suggestion**: Restore `abs(value) < 1e-30` or machine epsilon as the default safety floor.

---

### Finding C: Platform Coupling via Private Windows CRT DLLs
- **File**: `histra/_framework_math.py` (lines 16–53)
- **Problem**: On Windows, the code loads `ucrtbase_clr0400.dll` or `msvcr120_clr0400.dll` via `ctypes` to emulate .NET Framework `pow` and `atan` rounding. On Linux, it falls back to standard `math.pow`.
- **Risk**: The docstring concedes: *"bitwise agreement with the Windows runtime is not guaranteed on other platforms"*. This introduces platform-dependent numerical results. If bit-exactness is impossible on Linux anyway, loading private Windows DLLs adds fragile C-runtime dependencies for negligible practical gain.
- **Suggestion**: Standardize on standard IEEE-754 double precision (`math.pow` / NumPy), or isolate CRT emulation exclusively to a Windows-specific diagnostic module.

---

### Finding D: Invasive `float32` Truncations Degenerating Precision
- **Files**: `histra/elements/interface.py`, `histra/solver/mass_matrix.py`, `histra/elements/quad_loads.py`
- **Problem**: Sprinkling `np.float32(...)` and casting back to `float` across area calculations, gravity constants, and line loads:
  ```python
  GRAVITY_ACCELERATION = float(np.float32(980.6))
  density = float(np.float32(material.w)) / gravity
  twice = np.float32(twice + cross)
  ```
- **Risk**: Unnecessary Python object wrapping overhead in non-JIT sections, reduced geometric/physical accuracy, and cluttered, un-idiomatic code.
- **Suggestion**: Retain native double precision (`float64`) across core model physics.

---

### Finding E: Overfitting to a Single Benchmark ("Dhir")
- **Status Doc**: `docs/STATUS.md` confirms:
  > *"Historical Article/interface-chain evidence qualifies its recorded source and environment; it is not a fresh v1.5.0 rerun of those models."*
- **Risk**: Commits from v1.4.1 to v1.6.0 were tuned extensively to reproduce all 501 pushover steps of the Dhir bridge. The remaining 13 canonical Article Benchmark models have not been comprehensively freshly qualified against these modifications.
- **Suggestion**: Run the full Article Models release gate (`histra-article-benchmark`) across all 14 models before declaring v1.6.0 release readiness.

---

### Finding F: Deceptive Convergence vs Structural Equilibrium
- **Investigation**: `docs/investigations/dhir-equilibrium-diagnostics.md`
- **Problem**: The Dhir benchmark passes in C# solely because `Work < 0.002`. In reality, the translational residual unbalance at these "converged" states ranges from **3.08 kN to 11.67 kN** (and raw norm exceeds 4,500 due to generalized moment units).
- **Risk**: Accepting steps with >11 kN of out-of-balance force means the structure is physically out of equilibrium. Prioritizing C# parity here means silently accepting unphysical solutions.
- **Suggestion**: Maintain Python's independent equilibrium audit and provide a clear `parity_mode="strict_csharp"` vs `parity_mode="physics"` option so users know whether they are validating legacy software or evaluating structural safety.

---

## 3. Summary of Actionable Recommendations

1. **Optimize Snapshot Validation**: In `HystereticBatchRuntime.snapshot(reuse=...)`, bypass `shares_memory()` and buffer checks in subsequent iterations once verified, or disable reuse for models under 1 MB.
2. **Revert/Isolate `ConvergenceTest.get_copy()`**: Prevent silent mutation of force tests into displacement tests.
3. **Restore `ArcLength` Safeguards**: Enforce `abs(val) < 1e-30` instead of `val == 0.0` in constraint denominators.
4. **Clean up `float32` Casts**: Keep geometry and physics formulations in standard double precision.
5. **Run the 14-Model Article Benchmark**: Validate whether these Dhir-specific changes broke or altered results across the other 13 bridge models.
